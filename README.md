# 레거시 커머스 — 기술 부채를 재현하고, 계량한다

기술 부채를 안고 있는 레거시 코드를 재구현하고, 부채를 측정했다.
기억을 기반으로 재구성한 것이라 당시 세부 내역과는 다를 수 있다.

- 인덱스를 넣어도, 램을 16배 늘려도 안 풀리는 쿼리가 있다 — 상품 50만 건에서 응답 없음
- 결제 PG가 8초 지연되자 결제와 무관한 상품 목록이 107배 느려졌다
- 재고 5개 상품에 20명이 동시 주문하니 20건이 전부 성공하고 재고가 음수가 됐다

셋 다 직접 돌려볼 수 있다. 근거는 아래에 있다.

### 기술 스택

| 스택 | 이 저장소에서의 의미 |
|---|---|
| Spring 4.3 / Java 8 | 아직도 여러 현장에 살아있는 조합. Java 8을 쓰지만 람다도 스트림도 없다. 문법은 그 이전 세대다 |
| MyBatis | XML에 SQL을 직접 박는 방식 |
| JSP + Tiles | 화면과 서버가 한 몸인 구조 |
| MySQL 5.7 | 별도 컨테이너로 분리 |
| Bootstrap 4.6 / jQuery 3.7 | 화면단. 부채를 다루는 범위 밖이다 |

## 기술 부채

이 저장소의 핵심이다. 자세한 목록은 **[TECH_DEBT.md](TECH_DEBT.md)** 에서 확인한다. — 7개 영역, 35항목.

| 영역       | 대표 항목                                            |
|----------|--------------------------------------------------|
| 데이터 & 쿼리 | 관리자 검색이 전부 `LIKE '%키워드%'`, 걸러내지 못하는 조회 조건, 큰 `OFFSET` 페이징 |
| 구조 & 타입  | `HashMap<String,Object>` 만능주의(시그니처 84곳), 메서드명 규칙으로 잡은 트랜잭션 경계 |
| 동시성      | 원자적이지 않은 재고 차감, `MAX + 1` 채번, 화면에만 있는 중복 주문 방어   |
| 외부 연동    | 주문 트랜잭션 안의 PG 동기 호출, 타임아웃 없음, 로그로 끝나는 승인 취소 실패   |
| 보안       | CSRF 토큰 없음, 업로드 확장자 미검증, 이스케이프 없는 출력       |
| 에러 & 운영  | `e.printStackTrace()` 7곳, WAR 통짜 배포, 역할이 섞인 설정 파일 |
| 지우지 않은 것 | 미사용 SQL, 죽은 설정, 컬럼명 오타, 코드 밖에 있는 용어사전            |

부채를 나열하면 주장이지만, **계량하면 증거다.** 아래는 실제로 쟀다.

### 인덱스를 넣어도, 램을 늘려도 안 풀리는 것

아래의 표는 MySQL 5.7(당시 세대), 인덱스가 들어간 상태의 DB 실행시간이다.

| 상품 건수 | 목록 1페이지 | 마지막 페이지 | 가격순 정렬 |
|---:|---:|---:|---:|
| 1,000 | 1.4ms | 8.0ms (5.7배) | 11.4ms (8.1배) |
| 10,000 | 7.9ms | 87.2ms (11.0배) | 130.1ms (16.5배) |
| 100,000 | 65.4ms | 7,406ms (113배) | 9,322ms (143배) |
| 500,000 | 995.3ms | 응답 없음 | 응답 없음 |

목록 조회는 끝까지 버틴다. 상품 10만 건에서 65ms, 50만 건에서도 1초다.
여기까지는 인덱스가 감당한다.

그런데 마지막 페이지와 가격순 정렬은 격차가 벌어지다 끊긴다.

병목은 세 층으로 갈린다.

| 층 | 무엇으로 풀리나 | 해당 항목                                          |
|---|---|------------------------------------------------|
| 1 | 인덱스 | 조인 컬럼 풀스캔, 회원, 기간 조회                           |
| 2 | 장비(램) | 대용량 디스크 읽기 — 버퍼풀 16배에 2.4~3.6배                 |
| 3 | 어느 것으로도 안 됨 | 큰 `OFFSET`, 조인 컬럼 정렬, `LIKE '%x%'`, 선택도 95% 조건 |

50만 건에서 버퍼풀을 32MB → 512MB로 늘리자 목록 조회는 995ms → 415ms가 됐지만,
마지막 페이지와 가격순 정렬은 여전히 응답이 없다.

3층은 **쿼리와 화면 설계를 바꿔야 풀린다.** 큰 `OFFSET`을 없애려면
"마지막 페이지로 점프" 를 포기해야 한다. 개발팀 혼자 정할 수 있는 문제가 아니다.

측정 방법은 [bench/README.md](bench/README.md), 결과는 [bench/RESULT.md](bench/RESULT.md) 에 있다.

### 결제 지연이 상관없는 화면까지 멈춘다

PG를 8초 지연시키고 주문 8건을 동시에 넣으면,
결제와 무관한 상품 목록이 0.057초 → 6.12초가 된다. 107배 늘어났다.
커넥션 풀 8개가 전부 PG 응답을 기다리는 주문 스레드에 묶이기 때문이다.

### 재고보다 많이 팔린다

재고 5개짜리 상품에 20명이 동시에 주문하면 20건이 전부 성공한다.
그런데 실제 차감은 9회뿐이고 남은 재고는 -4 다.

재고가 음수로 내려가는 순간 `0 = 재고 미관리` 규칙과 충돌해
차감이 아예 멈추기 때문에, 나머지 11건은 재고와 무관하게 주문이 되었다.

### 동시 요청이 서로를 덮어쓴다

회원가입 20건을 동시에 넣으면 14건이 실패한다. 아이디는 전부 다른데도 그렇다.
`MAX + 1` 채번이라 같은 순간에 읽은 요청들이 같은 번호를 만들고, PK 충돌로 깨진다.

세 가지 모두 직접 돌려볼 수 있다 — [repro/](repro/)

> 숫자는 이렇게 검증했다 — 측정값이 조인 방식 차이처럼 보였는데 실행계획을 떠보니
> 두 계획이 동일했다. 원인은 측정 순서(워밍업 편향)였고, 방법을 고쳐 전부 다시 쟀다.
> 과정은 [bench/RESULT.md](bench/RESULT.md) 5절.

## 빠른 실행

필요한 것 — JDK 8, Docker

```bash
docker compose up -d      # DB (MySQL 5.7, localhost:3307)
mvn tomcat7:run-war       # 앱  → http://localhost:8080
```

| | 계정 | 비밀번호 |
|---|---|---|
| 회원 | `user01` / `user02` / `user03`(휴면) | `password123` |
| 관리자 | `admin01` / `admin02` | `password123` |

- 관리자 화면 : http://localhost:8080/admin/login.do
- JDK 8이 아니면 빌드가 실패한다 (`java.version=1.8`)
- DB 데이터는 유지된다. 초기 상태로 되돌리려면 :
  `docker compose down && docker volume rm commerce-legacy_commerce-db-data && docker compose up -d`

### 한 바퀴 둘러보기

```
로그인(user01) → 상품 목록에서 검색 & 정렬 → 상세에서 장바구니 담기
  → 장바구니에서 선택 주문 → 무통장 결제(입금자명) → 주문완료
  → 마이페이지 주문내역 → 주문상세 → 주문취소(재고 복원 확인)
```

관리자(`admin01`)로는 상품 등록 → 주문관리에서 상태 변경(10→20→30) → 배송정보 등록까지.
주문상태는 한 단계씩만 올라가고, 배송정보를 넣으면 배송중(40)으로 자동 전환된다.

### 실제로 도는 범위

껍데기가 아니다. 아래는 화면에서 끝까지 동작한다.

- 회원 — 약관동의 → 정보입력(아이디 중복확인) → 가입 → 로그인
- 상품 — 목록(카테고리 3단 / 검색 / 정렬 / 페이징), 상세(대표/상세 이미지)
- 주문 — 장바구니(선택주문) → 주문서 → 결제(무통장 / 카드 PG 승인) → 완료
  - 재고 차감/복원, 소진 시 품절 전환 (단, 동시 주문에서는 어긋난다 — 아래 참고)
  - 무통장은 입금자명 / 계좌 / 입금기한 안내
- 마이페이지 — 주문내역(기간검색) / 주문상세 / 주문취소
- 관리자 — 상품/카테고리 관리, 주문관리(상태 변경 / 배송정보 등록), 송장 조회
