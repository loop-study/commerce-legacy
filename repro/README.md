# repro — 부채를 직접 재현해보기

부채를 나열하면 주장이지만, 재현되면 증거다.

쿼리·데이터 영역은 [bench/](../bench/) 에서 측정한다.
여기는 측정으로는 안 잡히는 부채 — 동시성과 외부 연동 — 를 재현한다.
둘 다 요청을 동시에 던져야 드러나므로 단독 측정으로는 절대 안 나온다.

> 부채 전체 목록은 [../TECH_DEBT.md](../TECH_DEBT.md).

## 준비

```bash
docker compose up -d      # DB
mvn tomcat7:run-war       # 앱 (전개된 WAR 를 서비스한다)
```

## `concurrent-signup.sh` — MAX + 1 채번이 같은 번호를 내준다

```bash
./repro/concurrent-signup.sh 20
```

회원번호를 이렇게 만든다.

```java
String maxMbrNo = joinMapper.selectMaxMbrNo();   // ① 읽고
int seq = parseInt(maxMbrNo.substring(1)) + 1;   // ② 더하고
joinMapper.insertJoinMbr(vo);                    // ③ 넣는다
```

①과 ③ 사이에 다른 요청이 끼어들면 둘이 같은 번호를 받는다.
`MBR_NO` 는 PK 라 뒤늦은 쪽의 INSERT 가 깨지고, 그 요청은 그대로 실패한다.
재시도도, 대체 채번도 없다.

실측 (20건 동시 요청)

```
가입 시도 : 20 건
실제 생성 :  6 명
실패      : 14 건        ← 아이디는 전부 달랐다
```

아이디를 서로 다르게 주기 때문에, 실패의 원인은 중복 아이디가 아니라 채번 충돌이다.
상품코드(`selectMaxPrdCd`)·카테고리코드(`selectMaxCatCd`)도 같은 구조다.

> 스크립트는 끝나면 자기가 만든 계정을 지운다.

## `oversell.sh` — 재고보다 많이 팔린다

```bash
./repro/oversell.sh 5 20      # 재고 5개에 20명이 동시에
```

재고 처리가 조회 → 판단 → 차감 으로 나뉘어 있고, 차감 UPDATE 에 재고 조건이 없다.

```java
int qty = orderMapper.selectPrdStockQty(map);   // ① 읽고
if (qty > 0) {                                  // ② 판단하고
    orderMapper.updatePrdStockDecrease(map);    // ③ 뺀다
}
```
```sql
UPDATE TB_PRD_MST SET STOCK_QTY = STOCK_QTY - ${ordQty}
WHERE PRD_CD = #{prdCd}        -- 재고가 얼마든 그냥 뺀다
```

①과 ③ 사이에 다른 요청이 끼어들면 둘 다 "재고 있음" 으로 판단하고,
차감은 조건 없이 실행되므로 재고가 음수로 내려간다.

실측 (재고 5개 / 동시 20건)

```
팔려야 할 수량 :  5 개
실제 주문 성공 : 20 건      ← 전부 성공했다
실제 차감      :  9 회      ← 성공 건수와 다르다
남은 재고      : -4
```

**성공 20건인데 차감이 9회뿐인 것이 요점이다.** 두 단계로 무너진다.

1단계 — 조회와 차감이 분리돼 있고 차감 `UPDATE` 에 재고 조건이 없어,
동시 요청이 서로를 지나치며 재고가 0 아래로 내려간다.

2단계 — 0 이하가 되면 차감이 멈춘다.

```java
if (salePssbQty > 0) {          // 0 이하면 통째로 건너뛴다
    updatePrdStockDecrease(..);
}
```

이 코드에서 `0` 은 "재고 미관리(무제한)" 를 뜻한다.
재고가 음수로 내려가는 순간 그 의미와 부딪힌다. 성공한 20건 가운데 11건은
재고를 건드리지도 못한 채 통과했다.

> 실행마다 차감 횟수가 8~11회 사이로 흔들린다. 타이밍에 달렸다.

> `${ordQty}` 도 눈여겨볼 것. `#{}` 가 아니라 문자열 치환이다.

## `pg-delay.sh` — 결제 지연이 상관없는 화면까지 멈춘다

```bash
./repro/pg-delay.sh
DELAY_MS=8000 ORDERS=16 ./repro/pg-delay.sh   # 창을 길게
```

결제 PG 를 주문 트랜잭션 안에서 동기 호출하고, 타임아웃도 없다(`pg.api.timeout=0`).
PG 가 느려지면 주문 스레드가 DB 커넥션을 쥔 채 대기하고,
커넥션 풀(기본 8개)이 마르면 결제와 아무 상관 없는 상품 조회까지 멈춘다.

실측 (PG 8초 지연 + 주문 8건 동시)

```
1. 지연 없음     상품 목록  0.057s
2. PG 8초 지연   상품 목록  6.116s   ← 107배
3. 지연 해제     상품 목록  0.060s
```

결제와 무관한 상품 목록이 6초가 됐다.

> 뒤쪽 측정이 정상으로 돌아오는 것은 주문 8건이 8초 만에 끝나 커넥션이 반납되기 때문이다.
> 실제 장애에서는 주문이 계속 들어오므로 그 상태가 지속된다. `ORDERS` 를 늘리면 창이 길어진다.

## 알려진 함정

- `tomcat7:run-war` 는 `target/classes` 가 아니라 전개된 WAR 를 서비스한다.
  `target/classes/messages/...` 를 고쳐도 앱은 눈도 깜짝 안 한다.
  스크립트는 `target/*/WEB-INF/classes/` 를 찾아서 고친다. (실제로 한 번 당했다)
- `messageSource` 는 `cacheSeconds=60` 이라 설정을 고쳐도 최대 60초 뒤에 반영된다.
  스크립트는 mock PG 를 직접 찔러 반영을 확인한 뒤 진행한다.
- 채번 충돌은 타이밍이다. 한 번에 안 나오면 요청 수를 늘려 다시 돌린다.
- 두 스크립트 모두 DB 를 실제로 바꾼다. 개발 DB 에서만 돌릴 것.

## 여기 없는 것

- CSRF — 토큰이 없다는 건 코드로 확인되지만, 재현하려면 외부 출처 페이지가 필요하다
- XSS — 화면 출력은 `<c:out>` 으로 이스케이프되어 있다
- `pageSize` 상한 — 유틸에는 상한이 없지만 컨트롤러 6곳이 전부 값을 덮어써서
  현재는 외부에서 뚫리지 않는다. 한 곳만 빠뜨리면 뚫리는 잠재 부채다
