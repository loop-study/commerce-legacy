# bench — 성능 측정 환경

레거시 코드가 얼마나 느리고 왜 느린지를 숫자와 실행계획으로 규명한다.
이 저장소가 지고 있는 여러 부채 중 쿼리·데이터 영역을 다룬다.

> 진단만 한다. 쿼리를 다시 짜거나 구조를 바꾸지 않는다.
> 인덱스는 이미 들어가 있다. 조인·조회 컬럼에 걸려 있는 상태에서 잰다.
> 여기서 보려는 것은 그러고도 남는 것이다.

- 앱도 같은 MySQL 5.7 을 쓰지만(3307), 측정은 별도 컨테이너(3308)로 한다
- 스키마는 앱 것(`src/main/resources/db/schema.sql`)을 그대로 적재한다. 사본이 없어 어긋날 수 없다
- 앱 개발 DB 는 건드리지 않는다
- 부채 전체 목록은 [../TECH_DEBT.md](../TECH_DEBT.md), 측정 결과는 [RESULT.md](RESULT.md)

---

## 빠른 실행

```bash
cd bench
./run.sh init 3000    # 기동 + 스키마 + 상품 3천건 (규모 지정, 기본 3000)
./run.sh bench        # 6개 쿼리 측정
./run.sh explain q1   # 왜 느린지 실행계획
./run.sh down         # 폐기
```

규모를 바꿔가며 한 번에 보려면:

```bash
./run.sh sweep        # 1천 → 3천 → 5천 → 1만 연속 측정
```

> 당시 세대 엔진에서는 1만 건부터 이미 응답이 없다. 그 지점까지가 곡선이다.

## 명령어

| 명령 | 설명 |
|------|------|
| `./run.sh init [규모] [버전]` | 기동 + 스키마 + 데이터 적재 (기본 `3000` `5.7`) |
| `./run.sh info` | 버전 / 건수 / 분포 / 데이터 크기 / OFFSET |
| `./run.sh bench [라벨]` | 6개 쿼리 측정 |
| `./run.sh explain q1` | 실행계획 (왜 느린가) |
| `./run.sh coldrun q1` | 재시작 후 콜드/웜 비교 |
| `./run.sh sweep [버전]` | 규모를 바꿔가며 연속 측정 |
| `./run.sh down` | 컨테이너 폐기 |

## 무엇을 어떻게 재는가

### 1. 당시 세대의 엔진으로 잰다

MySQL 5.7 을 쓴다. 당시 운영 환경이 MySQL 5.x 세대였고,
5.7 은 인덱스 없는 조인을 Block Nested Loop 로 처리한다 — 당시와 같은 방식이다.

```
using_join_buffer: Block Nested Loop     ← EXPLAIN 에 그대로 찍힌다
```

> 최신 엔진으로 재지 않는다. MySQL 8 에는 hash join 이 있어 같은 SQL 이
> 훨씬 덜 느리게 나온다. 그걸로 재면 "인덱스 없어도 별로 안 느린데?" 라는
> 엉뚱한 결론이 나온다.
>
> 엔진 세대를 올리는 것은 그 자체로 개선 항목이라 레거시 기준선에 섞지 않는다.

### 2. 인덱스는 당시처럼 넣어둔다

앱의 `schema.sql` 을 그대로 쓴다. 조인·조회 컬럼에 인덱스 5개가 들어 있다.

```sql
KEY IX_PRD_IMG_01  (PRD_CD, IMG_TP_CD, SORT_SEQ)   -- 목록 조회 조인
KEY IX_ORD_MST_01  (MBR_NO, ORD_DT)                -- 마이페이지 주문내역
KEY IX_ORD_MST_02  (ORD_DT)                        -- 관리자 기간검색
KEY IX_CART_01     (MBR_NO)                        -- 장바구니
KEY IX_ORD_TEMP_01 (MBR_NO)                        -- 임시주문 조회
```

`PRD_STAT_CD` 에는 넣지 않았다. 조회 조건에 95%가 통과해서 옵티마이저가
쓰지 않기 때문이다. 넣으면 "만들었는데 안 쓰이는 인덱스" 가 하나 늘 뿐이다.

### 3. 규모를 바꿔가며 잰다

부채는 데이터가 적을 땐 보이지 않는다. 오픈 직후엔 멀쩡하다가
몇 달 뒤에 터지는 이유가 그것이다. 한 지점만 재면 그 성질을 못 보여준다.

| 규모 | 무엇을 보려고 |
|---|---|
| 1천 | 기준선 |
| 3천 | 격차가 보이기 시작 |
| 5천 | |
| 1만 | 격차가 확실해진다 |

한 지점만 재면 "별로 안 느린데?" 로 끝난다. 여러 점을 이어야
어떤 쿼리가 데이터와 함께 나빠지는지가 드러난다.

### 4. 데이터 분포를 설계한다

`INSERT` 를 수천 줄 적는 대신 숫자 테이블 cross join 으로 행을 파생시킨다.
분포는 의도적으로 설계했다.

| 항목 | 설계 | 왜 |
|------|------|-----|
| 상품명 | 프라이팬/냄비/수건/과자/건강즙/로션 각 1/6 | `LIKE '%프라이팬%'` 가 0건이면 결과 처리 비용이 없어 실제보다 빠르게 나온다 |
| 상태 | 판매중 85% / 품절·예약·종료 각 5% | 조회 조건에 95%가 걸린다 → 조건문이 사실상 아무것도 안 걸러낸다 |
| 카테고리 | 소분류 각 1/6 | 소분류까지 좁혀야 겨우 1/6 |
| 등록일 | 1분 간격 분산 | `ORDER BY REG_DT DESC` 정렬 실험용 |

> 재귀 CTE(`WITH RECURSIVE`)가 더 짧지만 MySQL 8.0 전용 문법이라 5.7 에서 안 돈다.
> 당시 세대로 재려면 5.7 에서 도는 방식이어야 한다.

### 5. 측정은 DB 안에서, 워밍업을 버리고 중앙값으로

셸에서 `time` 으로 재면 접속·연결 비용이 섞이는데 그게 쿼리보다 클 수도 있다.
MySQL 자신이 기록하는 실행시간(`SHOW PROFILES`)을 쓴다.

같은 쿼리도 잴 때마다 다르다(백그라운드 작업, OS 스케줄링).
1회만 재면 잡음에 휘둘리고, 평균은 한 번 크게 튄 값이 전체를 끌어올린다.
중앙값은 튄 값에 흔들리지 않는다.

```
측정: 12ms, 13ms, 12ms, 89ms(잡음), 13ms
평균  = 27.8ms  ← 왜곡됨
중앙값 = 13ms   ← 실제에 가까움
```

앞의 3회는 버린다. 버퍼풀이 차가운 상태에서 시작하면 먼저 도는 쪽이
워밍 비용을 혼자 떠안아, 조건이 같은데도 다른 숫자가 나온다.
실제로 이 함정에 걸린 적이 있다([RESULT.md](RESULT.md) 5절).

제한시간은 20초다. 인덱스를 뺀 상태로 재면 조인 비용이
`O(상품수 × 이미지수)` 로 폭발해 한 번 실행에 몇 시간이 걸린다.
끝까지 기다리는 건 의미가 없고, "제한시간 내 응답 없음" 자체가 결과다.

### 6. 실행계획으로 원인을 짚는다

측정 시간이 "얼마나 느린가" 라면, `EXPLAIN` 은 "왜 느린가" 를 말해준다.
숫자만으로는 원인을 말할 수 없으므로 반드시 함께 본다.

| 항목 | 의미 |
|------|------|
| `access_type: ALL` | 풀스캔 — 테이블을 처음부터 끝까지 |
| `access_type: eq_ref` | PK 로 1건만 집어옴 |
| `rows_examined_per_scan` | 훑을 예정인 행 수 |
| `using_filesort` | 정렬을 따로 하고 있다 |
| `using_join_buffer: Block Nested Loop` | 조인 상대를 반복해서 훑고 있다 |

5.7 은 `FORMAT=TREE` 가 없어 `FORMAT=JSON` 을 쓴다.
`run.sh` 가 읽기 좋게 요약해서 보여준다.

## 측정 대상 쿼리

앱의 `PrdSQL.selectPrdList` / `selectPrdListCnt` 에서 MyBatis 태그만 걷어낸 것이다.
6가지를 고른 이유는 각각 다른 것을 보려고다.

| 쿼리 | 무엇을 보려고 |
|------|--------------|
| q1 목록 1페이지 | 조인 3개 + 정렬의 기본 비용 |
| q2 목록 마지막페이지 | `OFFSET` 이 커지면 왜 느려지나 |
| q3 카테고리 필터 | 조건을 걸어도 안 줄어드나 |
| q4 키워드 검색 | `LIKE '%x%'` 앞 와일드카드의 대가 |
| q5 총건수 COUNT | 조인이 없는 대조군 |
| q6 가격순 정렬 | 조인한 다른 테이블 컬럼으로 정렬하면 |

> q5 가 대조군이다. 다른 항목이 제곱으로 늘 때 이것만 선형으로 늘면,
> 원인이 조인이라는 뜻이다.

## 알려진 한계 (결과 해석 시 감안할 것)

- DB 실행시간만이다. 실제 화면 응답에는 JSP 렌더링·Tiles 조립·네트워크가 더해진다.
  이 측정값은 하한값이다.
- 단일 접속 측정이다. 동시 접속 부하는 재지 않는다. 실제 장애는 동시성이 겹칠 때 커진다.
- 버퍼풀 32MB 설정은 실측 구간에서 아무 영향이 없었다. 원래 대용량 구간을 겨냥한 값인데,
  상품 5천 건의 데이터가 3.5MB 라 버퍼풀에 전부 들어간다.
  콜드와 웜이 같게 나온 것이 그 증거다. 이 느림의 정체는 CPU 계산 시간이다.
- 엔진이 당시 것과 완전히 같지는 않다. 세대와 조인 처리 방식은 맞췄지만,
  동일한 환경은 아니다.
- q4 의 `LIKE` 실험은 DB 조회 전반에 해당하는 이야기다.
  원본 FO 검색은 외부 검색솔루션이었으므로 그쪽의 재현은 아니다.
  다만 원본 관리자 검색은 DB `LIKE` 였고, 그 패턴은 정확한 재현이다.
