# 성능 측정 결과 — 인덱스를 넣어도 남는 것

> 측정 환경과 방법은 [README.md](README.md), 부채 전체 목록은 [../TECH_DEBT.md](../TECH_DEBT.md).
> 측정일 2026-08-12 / MySQL 5.7.44

여기서는 진단만 한다. 쿼리를 다시 짜거나 구조를 바꾸지 않는다.
인덱스는 이미 들어가 있다. 조인·조회 컬럼에 걸려 있는 상태에서 잰 값이다.
여기서 보려는 것은 그러고도 남는 것이다.

---

## 1. 측정 환경

| | |
|---|---|
| 엔진 | MySQL 5.7.44 — 당시 세대 |
| 호스트 | darwin / x86_64, Docker 20.10.5 |
| 인덱스 | 조인·조회 컬럼에 5개 (아래) |
| 데이터 | 상품 1천 ~ 50만 (이미지는 각 3배) |
| 버퍼풀 | 32MB (일부 구간은 512MB 와 비교) |
| 측정 | 워밍업 3회 버린 뒤 5회 중앙값, 단일 접속 |

```sql
KEY IX_PRD_IMG_01  (PRD_CD, IMG_TP_CD, SORT_SEQ)   -- 목록 조회 조인
KEY IX_ORD_MST_01  (MBR_NO, ORD_DT)                -- 마이페이지 주문내역
KEY IX_ORD_MST_02  (ORD_DT)                        -- 관리자 기간검색
KEY IX_CART_01     (MBR_NO)                        -- 장바구니
KEY IX_ORD_TEMP_01 (MBR_NO)                        -- 임시주문 조회
```

> `PRD_STAT_CD` 에는 인덱스를 넣지 않았다. 조회 조건에 95%가 통과해서
> 옵티마이저가 쓰지 않기 때문이다. 넣으면 "만들었는데 안 쓰이는 인덱스" 가 하나 늘 뿐이다.

### 왜 5.7 인가

당시 운영 환경은 MySQL 5.x 세대였다.
최신 엔진(MySQL 8)에는 hash join 이 있어 같은 SQL 이 훨씬 덜 느리게 나온다.
그걸로 재면 "인덱스 없어도 별로 안 느린데?" 라는 엉뚱한 결론이 나온다.
엔진 세대를 올리는 것은 그 자체로 개선 항목이라 레거시 기준선에 섞지 않았다.

## 2. 인덱스가 제곱을 선형으로 바꿨다

같은 쿼리를 인덱스 전후로 잰 값이다. (상품 목록 1페이지, ms)

| 상품 건수 | 인덱스 전 | 인덱스 후 | |
|---:|---:|---:|---|
| 1,000 | 736.5 | 1.4 | 526배 |
| 3,000 | 6,395.3 | 2.7 | 2,368배 |
| 5,000 | 17,649.0 | 4.1 | 4,304배 |
| 10,000 | 응답 없음 | 7.9 | — |

인덱스 전에는 데이터가 5배 늘 때 조회가 24배 느려졌다(제곱).
인덱스 후에는 5배 늘 때 2.9배 — 선형이다.

**여기까지가 인덱스로 풀리는 부분이다.**

## 3. 규모를 키우면 다시 갈라진다

인덱스가 들어간 상태에서 상품 1천 → 50만까지 잰 값이다. (ms, 버퍼풀 32MB)

| 상품 건수 | 데이터 | q1 목록<br>1페이지 | q2 마지막<br>페이지 | q3 카테고리<br>필터 | q4 키워드<br>검색 | q5 총건수<br>COUNT | q6 가격순<br>정렬 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 1MB | 1.4 | 8.0 | 1.5 | 2.1 | 0.7 | 11.4 |
| 3,000 | 2MB | 2.7 | 24.9 | 3.3 | 4.3 | 1.6 | 32.7 |
| 5,000 | 4MB | 4.1 | 43.9 | 5.2 | 7.1 | 2.5 | 57.3 |
| 10,000 | 9MB | 7.9 | 87.2 | 9.4 | 12.7 | 4.4 | 130.1 |
| 100,000 | 65MB | 65.4 | 7,406 | 102.9 | 120.8 | 41.0 | 9,322 |
| 500,000 | 321MB | 995.3 | timeout | 1,200.7 | 1,395.8 | 801.4 | timeout |

### 목록 조회는 끝까지 버틴다

q1 은 1천 건 1.4ms 에서 50만 건 995ms 까지, 데이터 500배에 711배다. 거의 선형이다.
10만 건 지점에서 65ms 다. 목록 화면은 이 정도 규모를 인덱스만으로 감당한다.

### q2·q6 은 격차가 벌어지다 끊긴다

| q1 대비 | 1,000건 | 10,000건 | 100,000건 | 500,000건 |
|---|---:|---:|---:|---:|
| q2 마지막 페이지 | 5.7배 | 11.0배 | 113배 | 응답 없음 |
| q6 가격순 정렬 | 8.1배 | 16.5배 | 143배 | 응답 없음 |
| q4 키워드 검색 | 1.5배 | 1.6배 | 1.8배 | 1.4배 |
| q3 카테고리 필터 | 1.1배 | 1.2배 | 1.6배 | 1.2배 |

q3·q4 는 q1 과 나란히 간다. q2·q6 만 데이터가 늘수록 뒤처지다가 끊긴다.

---

## 3-1. 램을 늘리면 어디까지 풀리는가

50만 건에서 버퍼풀만 32MB → 512MB 로 바꿔 다시 쟀다.
데이터가 321MB 이므로 512MB 면 전부 램에 들어간다.

| | 32MB | 512MB | |
|---|---:|---:|---|
| q1 목록 1페이지 | 995.3 | 415.1 | 2.4배 빨라짐 |
| q3 카테고리 필터 | 1,200.7 | 424.4 | 2.8배 |
| q4 키워드 검색 | 1,395.8 | 585.5 | 2.4배 |
| q5 총건수 COUNT | 801.4 | 220.0 | 3.6배 |
| q2 마지막 페이지 | timeout | timeout | 변화 없음 |
| q6 가격순 정렬 | timeout | timeout | 변화 없음 |

대부분은 램으로 완화된다. 큰 규모에서는 디스크가 실제 병목이었다는 뜻이다.

**그런데 q2·q6 은 램을 16배 늘려도 그대로다.**

> 앞선 측정에서 내린 "디스크가 아니라 CPU다" 라는 결론은 규모에 한정된 것이었다.
> 상품 5천 건(데이터 3.5MB)에서는 전부 램에 있어 CPU 가 맞았지만,
> 50만 건에서는 디스크가 확실히 병목이다. 규모에 따라 병목이 옮겨간다.

## 4. 왜 그 둘만 남는가

### 4-1. 큰 `OFFSET` 은 "건너뛰기"가 아니다 (q2)

DB 는 `LIMIT 12 OFFSET 9492` 를 "9,492개를 건너뛴다" 로 처리하지 않는다.
9,504개를 전부 만들어놓고 앞의 9,492개를 버린다.

인덱스가 있어도 버릴 행을 만드는 일 자체는 줄지 않는다.
그래서 페이지 번호가 뒤로 갈수록, 데이터가 많을수록 나빠진다.

> 커서 기반 페이징으로 가야 풀리는데, 그러면 "마지막 페이지로 점프" 를 포기해야 한다.
> 기술만으로 끝나지 않고 화면 설계가 함께 바뀌는 문제다.

### 4-2. 정렬 기준이 조인해서 붙인 테이블에 있다 (q6)

가격순 정렬의 기준 `B.CASH_DISC_PRC` 는 주 테이블 `A` 가 아니라 `B` 에 있다.
정렬 기준값을 알려면 먼저 조인해서 붙여야 하므로,
`LIMIT 12` 를 걸어도 12건만 읽고 끝낼 방법이 없다.

```
* Using filesort
  - A  ALL     rows=9746            ← 전량을 읽고
  - B  eq_ref  rows=1               ← 하나씩 붙인 다음에야
  ...                                  정렬할 수 있다
```

`TB_PRD_PRC` 조인은 PK 라 이미 최적이다. 인덱스로 더 할 게 없다.
가격을 상품 테이블로 비정규화하거나, 정렬 전용 구조를 따로 두어야 풀린다.

### 4-3. `LIKE '%키워드%'` 는 인덱스가 손댈 수 없다 (q4)

인덱스는 "앞에서부터 정렬된" 자료구조다. 시작점을 모르면 쓸 수 없다.
전화번호부에서 "김"으로 시작하는 사람은 바로 찾지만,
"이름 중간에 '철'이 들어간 사람" 은 처음부터 다 넘겨봐야 하는 것과 같다.

이 저장소에서는 격차가 1.7배로 작지만, 원본 관리자에서는 조회 쿼리 대부분이 이 형태였다.
검색 조건이 늘어날수록 이 비용이 누적된다.

### 4-4. 조회 조건은 여전히 아무것도 걸러내지 않는다

```sql
WHERE A.PRD_STAT_CD IN ('30', '40', '50')
```

1만 건 중 9,500건(95%) 이 통과한다. 판매종료 5%만 빼는 조건이라 사실상 전건 조회다.
여기에 인덱스를 만들어도 옵티마이저가 쓰지 않는다 — 걸러지는 게 없으니
인덱스로 찾아 원본을 다시 읽느니 전부 훑는 게 싸기 때문이다.

## 5. 이 숫자를 믿어도 되는가 — 측정 방법에서 겪은 함정

실험하다 당한 일이라 그대로 기록한다.

이전 측정에서 같은 쿼리가 조건에 따라 다른 값을 보였다.
차이의 원인처럼 읽히는 숫자였는데, `EXPLAIN` 을 떠보니 두 계획이 완전히 동일했다.

원인은 측정 순서였다. 먼저 도는 쪽이 버퍼풀 워밍 비용을 혼자 떠안았던 것이다.
순서를 뒤집어 다시 재니 차이가 사라졌다.

앞의 3회를 버리고 뒤의 5회만 채택하도록 고쳤고, 이 문서의 모든 숫자는 그 방법으로 잰 값이다.

> **계획이 같은데 시간이 다르면, DB 보다 측정 방법을 먼저 의심해야 한다.**

## 6. 한계

- DB 실행시간만이다. 실제 화면 응답에는 JSP 렌더링·Tiles 조립·네트워크가 더해진다.
  이 문서의 수치는 하한값이다
- 단일 접속 측정이다. 동시 접속 부하는 재지 않았다. 실제 장애는 동시성이 겹칠 때 훨씬 커진다
- 엔진이 당시 것과 완전히 같지는 않다. 세대(MySQL 5.x)와 조인 처리 방식
  (Block Nested Loop)은 맞췄지만, 동일한 환경은 아니다
- q4 는 FO 검색 기준이다. 원본 FO 상품검색은 외부 검색솔루션이었으므로 그쪽은 재현이 아니다.
  다만 원본 관리자 검색은 DB `LIKE` 였고, 그 패턴은 정확한 재현이다

## 7. 이 측정이 말하는 것

인덱스는 넣었다. 제곱이 선형이 됐고, 목록 조회는 4,000배 빨라졌다.

그리고 규모를 키우고 램을 늘리며 재보니, 병목이 세 층으로 갈렸다.

| 층 | 무엇으로 풀리나 | 해당 항목 |
|---|---|---|
| 1 | 인덱스 | 조인 컬럼 풀스캔 · 회원·기간 조회 |
| 2 | 장비(램) | 대용량에서의 디스크 읽기 — 버퍼풀을 16배 늘리니 2.4~3.6배 |
| 3 | 어느 것으로도 안 됨 | 큰 `OFFSET` · 조인 컬럼 정렬 · `LIKE '%x%'` · 선택도 95% 조건 |

3층이 이 측정의 핵심이다. **인덱스를 넣어도, 램을 16배 늘려도 `timeout` 그대로다.**

| 50만 건 | 버퍼풀 32MB | 버퍼풀 512MB |
|---|---|---|
| 목록 1페이지 | 995ms | 415ms |
| 마지막 페이지 | timeout | timeout |
| 가격순 정렬 | timeout | timeout |

이건 쿼리와 화면 설계를 바꿔야 풀린다.
큰 `OFFSET` 을 없애려면 "마지막 페이지로 점프" 를 포기해야 한다.
개발팀 혼자 정할 수 있는 문제가 아니다.

여기까지가 그 판단의 근거다. 고치는 것은 리팩토링 단계에서 다룬다.
